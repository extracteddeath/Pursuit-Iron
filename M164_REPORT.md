# M164 history & progression integrity

App **3.214.0**, build **770**, Pursuit Engine **0.62.5**. Based on M163.

## Reported issues addressed

1. A workout-history error could not be corrected in place.
2. A custom-program 10–15 double-progression target could display a rationale saying that reaching 10 reps earned a load increase.
3. The live engine path needed another explicit end-to-end authority audit after the recent progression fixes.

## History correction

Expanded History sessions now expose a pencil action. The correction sheet can edit date/time, session duration, and each logged set's load, reps and RIR. Sets can be added/removed and an erroneous lift can be removed. Structural provenance is intentionally locked: a correction cannot change the program, planned day, or week that owns the workout.

Saving a correction rebuilds `weight`, `reps`, session volume and completed-set count from the corrected raw sets. It also refreshes the app's latest-performance mirror. The lifter-model memo key now fingerprints raw performed-set evidence (including observed/target RIR) so RIR-only or equal-tonnage corrections invalidate readiness/coaching/progression caches.

## 10–15 double-progression bug

This was a **programming bug, not just wording**. Custom-plan overrides can exist as arrays such as `[10,15]` and `[2,2]`. The custom progression bridge converted the rep array with `String(value)`, producing `"10,15"`; its hyphen-only parser therefore read the target as `10–10`. That made the bottom of the intended range look like the top.

M164 uses the same canonical range parser as the workout prescription. For a 10–15 double-progression prescription:

- `10/10/10` at the current load -> **hold load, build toward 15**;
- `15/15/15` at the planned effort -> **increase by the next loadable increment and restart at 10**.

Custom cells also normalize array-shaped rep/RIR values before rendering, preventing the comma-form from leaking back into Program/Workout UI.

## Engine authority audit

The Pursuit Engine core remains **0.62.5**; no engine math was silently swapped in this release. The audit verifies:

- normal program creation returns an audit-passing Pursuit Engine 0.62.5 program;
- the shell stores immutable engine request/program snapshots;
- Program/Workout reads the engine-owned week cell;
- workout runtime realizes exactly the engine-owned working-set count;
- bottom-of-range completed work returns `add_reps`;
- top-of-range work across all prescribed sets returns `increase_load`;
- wizard/rebuild/cycle creation routes remain `pursuit-next-only`;
- generated-program next-session suggestions use `nextWorkoutSuggestionForShell`, which evaluates completed history through the Pursuit Engine performance evaluator.

User-authored custom/freestyle programs are deliberately not generated by Pursuit Engine. They use the separate shell bridge, which M164 now aligns with the same rep-range semantics and safety rules.
