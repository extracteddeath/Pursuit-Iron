# Pursuit Iron — master development plan
**Established:** 2026-11-24. **Target:** architecture/kotlin-engine-rebuild.
**Authority:** This operational plan implements [LAUNCH_BETA_SCOPE.md](LAUNCH_BETA_SCOPE.md). It does not waive its acceptance requirements or authorize a distributable build.

## End states and non-negotiables
- E1 — Complete source: one Kotlin numerical and training authority, full verified functional web-engine parity (not literal JS output equivalence), all known release-blocking defects closed, complete native core UI, secure and recoverable private storage, no legacy runtime or demo routes. Both required CI suites green on the integrated revision.
- E2 — Controlled device acceptance: only after E1 and explicit authorization to lift the APK freeze, build a private test artifact from the exact reviewed revision; pass real-device tests, correct failures and requalify impacted gates. No external distribution or AAB at this point.
- E3 — Several-month beta: all release gates satisfied including verified backup/restore, updates, accessibility, offline lifecycle, reproducible feedback and no known P0/P1 defects. Signed controlled distribution to the intended tester(s). Never silently reset data.
- E4 — Production decision: sustained real training evidence and stability, privacy/security review, supported update/restore path, issue resolution and explicit owner decision. No claim of superior results without matched evidence and independent review. No automatic public launch.
- Future goal-based Endless Plan improvements have their own post-beta milestone; existing web Endless Plan behavior remains in the parity inventory and must pass E1. Do not defer existing functionality by renaming it an enhancement.

## New findings: finite intake, severity and stage control

All findings enter a single ledger before work expands. Required fields: ID; date; source SHA and branch; origin (web report, Kotlin audit, CI, tester, research); exact reproduction or evidence; expected/actual; affected capability and canonical authority; severity; stage; disposition; regression ID; PR and verification SHA; status; reason for deferral. Deduplicate by root cause, not symptoms.

| Class | Definition | Action |
| --- | --- | --- |
| P0 — critical | Data loss/corruption, unauthorized access, unsafe or unexplained physical load issuance, cross-athlete contamination, impossible recovery of core data. | Stop affected work and release; isolate root cause, reproduce, fix canonical owner, add cross-route regression and verify integrated branch. |
| P1 — release blocker | Missing mandatory parity, wrong progression/volume/machine/day/phase decision, failed core UI/lifecycle, required CI regression, broken restore, consent or device flow. | If blocks active gate or corrupts its evidence, fix now. Otherwise assign earliest applicable stage with explicit dependency and do not certify affected gate; all must close before beta. |
| P2 — non-blocking defect | Usability, visual or performance problem with intact correct data and a usable core path. | Batch into relevant stage; if already passed, queue bounded polish/regression work. Escalate if accessibility or completion is actually blocked. Known minor limitations may be recorded only with explicit acceptance, never silently waived. |
| P3 — enhancement or investigation | New behavior beyond agreed baseline, speculative optimization, stylistic preferences, science hypotheses. | Record in future backlog with rationale; do not expand scope or interrupt current stage. Owner decides whether it becomes a new committed requirement. |

New web changes: compare against pinned baseline each gate. Existing required capabilities or defect corrections become parity deltas, assigned a row and stage. Brand-new enhancements require explicit scope decision; baseline changes are documented rather than silently moving the denominator. Never ignore an active required feature simply because it appeared after a snapshot. A fix on another branch is evidence to inspect, not automatically a Kotlin fix; reproduce the behavior and implement in canonical Kotlin.

Triage loop: reproduce → identify shared authority → classify → assign disposition → implement focused fix or backlog → test affected paths → update evidence and stage gate. A new finding only reopens affected gates and dependent evidence, not the whole plan. If three independent symptoms share a root cause, consolidate under one design change. Avoid speculative hardening with no reproducible risk, duplicated rules, or unbounded refactoring. When a stage passes, stop routine hunting in it and move to the next highest-priority gate; reopen only for demonstrated regression, new required scope or invalid evidence.

## Evidence and definition of done
- One row per capability and independently testable behavior; separate statuses: not inventoried, not implemented, implemented unverified, headless verified, real-store verified, source UI verified, device verified, accepted, failed or explicitly deferred optional. Not applicable requires rationale. Neither merged PR count nor lines of code are progress.
- Each mandatory row has source references, exact source/fixture SHA, intended result, matched web/Kotlin output where applicable, test IDs, verification date and reviewer/owner acceptance. Stale evidence must be rerun for affected dependencies. A successful CI workflow alone is not proof of every behavior.
- Report stage progress as passed required acceptance rows / total required rows, plus blockers and unverified rows; denominator versioned. Do not assign invented completion percentages. Distinguish source completion from actual device verification.
- Every PR: single coherent outcome, root-cause explanation, canonical numerical owner (if relevant), regression evidence, source compatibility and impact assessment. Both required CI workflows must pass on exact head; merge, then verify integrated revision. No test disabling, loosening expected results merely to pass, or APK shortcuts. Test-only/static checks must be labeled as such.
- Every development pass starts with the stage gate and active work item; ends with merged verified outcomes, submitted but unverified changes, newly discovered blockers, next work item and evidence updates. No routine approval request; ask only when a genuine product decision, external-device access, scope change or release authorization is required.

## Change control
The plan and ledger are maintained in Git. Update status as work completes. Owner approval is required to change release scope, remove required features, waive acceptance criteria, authorize APK production or distribute the beta.
