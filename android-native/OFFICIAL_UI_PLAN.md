# Pursuit Iron — official native UI plan

**Decision (2026-11-08): develop the official native UI in parallel with the
new Kotlin coaching engine.** This is not an instruction to switch production
away from the web app. The isolated Kotlin Lab is the integration baseline
until real device acceptance and engine-superiority evidence exist.

## Default appearance and user control

- **First-install default: Amethyst**, using the *exact* 20-theme web-app
  source palette already mirrored in `NativeDesignTokens.kt`: dark
  `#0C0913` background, `#181221` surface and lavender `#B388FF`
  accent. **Neon Lime `#D4FF3D` must not be the default.**
- Retain the entire original 20-theme selection, including Graphite, Ice,
  Patrol, Lilac and user-chosen Lime. Never rewrite any of their colors
  solely to enforce a new default.
- Preserve a previously selected valid theme in app-local appearance
  preferences; changes never modify workout journals, exercise prescriptions
  or owner-authenticated coaching receipts.
- Kotlin Lab needs a *functional* theme picker in More and Settings, live
  Material 3 color updates, and status/navigation bar contrast synchronized
  to the chosen light/dark theme. No launch-time-only or fake picker.
- Palette values remain shared tokens, rather than screen-local hardcoding.
  Verify first-install Amethyst, explicit persistence, an invalid-theme
  fallback, light/dark appearance and contrast in source and on device.

## Why UI work starts before engine completion

The Kotlin Lab already runs a testable onboarding, program, Train, History,
Coach and next-session route with persistent native training data. Waiting
for perfect forecasting would defer the most expensive usability findings
and create mismatched engine/UX requirements. But building polished static
screens first would also be a mistake: all major controls must use genuine
program and coaching domain states.

**Parallel ownership:** the engine can evolve its versioned decision models
and tests; native UI work consumes stable, typed preview/commit/history
interfaces. Any engine change that alters user decisions requires explicit
UI treatment (explanation, approval/rejection, error recovery), not a raw
data-class string or an implied automatic update.

## Recommended implementation phases

1. **Foundation now:** exact original theme tokens, Amethyst default, live
   picker, typography, contrast, spacing, motion, scaffold/navigation,
   keyboard handling, consistent action states, accessibility semantics and
   realistic empty/error/loading states. Keep the existing Material 3 Expressive
   component baseline; do not introduce an unrelated visual style.
2. **Usable core:** rebuild Home/Today, Plan and Train with one visual language.
   Make the session overview, next set, weight/reps/RIR controls, amplifier,
   warmup, rest timer, notes, skip and Finish correct in compact phone layouts,
   and preserve journal state across process death and orientation changes.
3. **Coaching and progression:** visually connect verified target-versus-actual
   History, Progress, exercise-level Coach, approved next workouts and custom
   adaptive cycles. Explanations must distinguish physiological estimates
   from confirmed actuals and explicitly preserve Manual/progression-only
   coaching modes. Nothing applies without consent.
4. **Release-quality acceptance:** exercise complete athlete journeys on
   physical Android devices and emulator, light/dark themes, large font,
   foldables, screen readers, bad network, interrupted writes, amended history
   and old installation update paths. Run paired JS vs Kotlin quality fixtures,
   record failures, and fix regressions before production replacement.

## Non-negotiable acceptance criteria

- A real user can move **onboarding → real customized program → preview →
  workout → saved/corrected History → next recommended workout** without raw
  IDs, blank screens or duplicated ownership.
- Per-set loads, reps, RIR, fatigue/recovery advice, progression and adaptive
  block decisions are generated by the versioned native engine and visibly
  explained. The UI must not invent values or silently reinterpret unknown RIR.
- All requested split/equipment/schedule/program constraints, workout
  variants, volume/time checks and custom-cycle workflows receive feature
  parity or explicit user-facing omissions before release.
- The default theme is Amethyst; actual selected theme persists on reopen;
  Lime never reappears as an implicit fallback; all web-app themes remain
  selectable.
- The official app earns a consistently signed, update-safe APK and
  complete device evidence. AAB production is deferred until the athlete
  prepares a Play Store listing. The disposable trial APK exists only to
  discover usability defects; source CI alone is not a release gate.
- No changes to the existing web app, production app package, saved training
  data or the other developer's native branch during this UI iteration.

## Workout reference pass — 2026-11-08

Both custom-cycle and Composer workout screens now share a persistent
Target/Last display preference and weight → reps → RIR reference strip.
Last uses corrected, authenticated saved observations from the latest same
program day, matching the exact exercise slot, warmup/working position and
amplifier part. Upper-day bench and Push-day bench remain independent.
Skipped/failed latest visits are shown as such; an older successful workout
is never selected instead. Unreported actual RIR remains unknown. Changing
the display cannot fill/edit/record any set field or alter a target.

The first-program preview and both workout paths use original curated
exercise names. Active sets display their position within warmups or working
sets, and the custom logger groups reps/RIR side by side on the phone.

**Next implementation priority:** validate these controls through a full
Android workout and large-text layouts, then continue the Plan/Coach screen
composition, functional parity and measured coaching improvements. Source
checks do not establish physical-device acceptance.
