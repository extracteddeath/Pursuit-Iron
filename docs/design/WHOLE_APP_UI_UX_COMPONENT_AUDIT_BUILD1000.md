# Pursuit Iron — whole-app UI/UX and shared-component audit

**Date:** 2026-10-30  
**Audited production baseline:** Build 1000, main at bc8e1b91f6946101a99b0c91dd2626588514dce8  
**Design target:** docs/design/PURSUIT_IRON_DESIGN_SPEC_V1.md (v1.0.0; proposed, not implementation certification)  
**Scope:** all root destinations, Program/Cycles, Workout/Focus, onboarding, secondary views, dialogs, state messaging and shared infrastructure.  
**Type of evidence:** inspected source and existing verification/contracts. This is an architectural and UX-contract audit, not a claim of actual screenshots, physical Android testing, or 14/14 surface acceptance.

## Executive decision

**Pause incremental CSS-only passes until the cross-screen control system is agreed and implemented in one pilot.** The existing primitives are good foundations but are not yet the default across the app. The biggest risk is inconsistent ownership: legacy raw buttons, surface variants, typography and dynamic theme styling coexist with the new design system, so local fixes can be visually neutralized by the cascade or create another near-duplicate pattern.

Do not interpret source counts as broken UI. A workout set stepper legitimately differs from a normal toolbar action; an intentionally prominent hero differs from a quiet inset card. Consolidation must follow function and state, not string similarity alone.

### Existing good foundations

- modules/ui-primitives.js already defines UiAction, UiChoice, UiRootHeader, UiSheetClose, UiStatus, UiSection and UiHeader.
- .wpb-ui-card, .wpb-ui-field and .wpb-ui-control already supply shared semantic CSS roles.
- modules/ui-disclosure.js provides InfoCard and interruptible MotionReveal.
- modules/ui-menu.js owns contextual menu rendering and opener focus behavior.
- modules/ui-motion.js owns important spatial motion; modules/ui-layout.js manages notice/nav/dock occlusion.
- Existing contract registry runs seven Chromium groups and source contracts. These are valuable regression safeguards, but do not substitute for design-image review or hardware evidence.

## 2. Target shared component vocabulary — adopt *before* large migrations

| Family | Canonical variants and roles | Shared owner | Screen-only responsibility |
|---|---|---|---|
| Action | primary (52px), secondary, tonal, text, icon (48px), danger/confirm; compact only if real 48px hit area | UiAction + shared CSS tokens | OnClick, pending policy, display text and consequences |
| Icon action | one 48px square hit box, stable icon size, focus-visible and disabled | UiAction icon / UiSheetClose | Rest, Skip, More, close-specific callback |
| Choice | chip, tabs, segmented, summary, multiselect; selected/focus/disabled parity | UiChoice + selection-track owner | User choice, aria-selected or aria-pressed as appropriate |
| Card | standard, inset, interactive, metric, warning/status, hero; separate anatomy from paint | .wpb-ui-card with *explicit* role variants; add UiCard only where useful | Order, contents, data and navigation semantics |
| Section/heading | page hero, screen section, section heading, eyebrow, supporting text | UiRootHeader/UiSection + type scale | One dominant job per screen |
| Text/number field | label, unit, helper/error, raw draft, select-all on focus, min 48px / 16px text | .wpb-ui-field / .wpb-ui-control; dedicated numeric stepper contract | Validation, loading/increment snap, saved value |
| Set logger | active/planned/complete/skipped/editing, consistent Target/Last and weight→reps→RIR | Dedicated Workout/Focus set-control family, not generic button cards | Training engine decisions and set writes |
| Dialog/sheet | header title + close, scroll body, fixed footer where applicable, safe-area and visual viewport | Shared sheet shell, focus and overlay geometry | Transaction, back/escape and destructive-confirm behavior |
| Menu | opener, keyboard focus, selected/danger items and bounded scrolling | ContextMenu | Action list and app-specific effects |
| Feedback | status, inline validation, snackbar, Undo, PR; one message owner | UiStatus/notices and accessible live-region policy | Truth of the operation, whether it is reversible |
| Metric/chart | units/scope/value, comparable history, missing data, accessible textual alternative | Shared metric typography and card anatomy | Actual analytical calculations |

**Do not** create twenty barely different button/card variants. A small vocabulary with narrow exceptions is the goal. Document an exception when a workout-specific control legitimately requires unique structure.

### Design-system acceptance decisions required

1. Use existing user-selected themes and semantic foreground/background roles, not a forced neutral/purple redesign.
2. Use existing 4/8/12/16/20/24/32/40px spacing rhythm as the default; parent owns gap and grouping.
3. Keep 48px effective action targets and 52px primary targets where the screen contract requires them; measure real hit rectangles rather than regex-searching min-height.
4. Prefer one accessible state contract: default, pressed/selected, pending, disabled, error and keyboard-focused.
5. Share interaction semantics, not only same-colored CSS. For example a selectable card must be an accessible action or contain one, not a clickable div with a decorative press animation.
6. Preserve the intentional distinction between standard screens and Focus/Workout while reusing the underlying field and action tokens.

## 4. Root-cause themes and concrete design opportunities

### A. Buttons and interactive cards — the most important shared-component mismatch

Current UiAction offers the right semantic variants, but many views still render raw native buttons with their own class/geometry. This is especially dense in Workout, Program, History and Settings. Do **not** replace every raw button mechanically: set steppers, tab triggers and context-menu items have specialized semantics. Instead classify every control as primary/secondary/tonal/icon/choice/stepper/menu or justify an exception, then migrate family by family.

**First acceptance target:** On Settings, Gallery, Program action bars and Home, comparable actions must have the same computed height, shape, typography, focus ring, busy/disabled style and theme paint. Only copy, icon and actual action differ.

### B. Card system — one card role, many unrelated implementations

The stylesheet has hundreds of selectors touching classes named card/tile/panel/surface. This does not mean hundreds of rendered cards; it means multiple visual families can independently own padding, radius, surface and dividers. Existing .wpb-ui-card use is significant but not universal. Define a normal card, inset content, metric card, interactive card, notice/warning and hero. Migrate **surface and spacing ownership** first; retain layout composition for highly specialized charts or workout rows.

**First acceptance target:** The same card role has one token-driven surface/radius/padding owner on Home, Plan, Progress, Profile and Settings; no screen adds another overriding paint copy.

### C. Two styling systems coexist

The 644KB app.css and 127KB dynamic StyleTag both own presentation; the latter interpolates live theme colors in ~285 places and has ~1,008 additional priorities. This explains why a local CSS edit may fail to produce the expected computed style and why arbitrary priority removal is unsafe. The desired long-term model is static shared CSS reading runtime theme variables, while React only writes **genuinely dynamic** values (e.g. animation position, progress bar, calculated load positions). Review selectors and specificity at the actual computed-style level before moving a slice.

**First acceptance target:** Any extracted region ends with one owner for static declarations, no net increase in priorities, explicit test of both light/dark and user-selected themes, and measured reduction in App/CSS debt.

### D. Typography and geometry lack full token adoption

Common literal 11px and 13px CSS text sizes remain. Radii range across many arbitrary-looking fixed values, although some are intentional. Use documented caption/support/body/heading type tokens and action/card/hero shape roles. Never flatten every surface to the same radius; the visual hierarchy needs deliberate contrast. Check 200% actual text and 320px layouts before replacing any fixed numeric type.

### E. Motion and layout need shared choreography, not more animations

Some CSS animation rules coexist with modules/ui-motion.js and screen-specific gesture code. Keep one owner for route movement, reveal heights, selected indicators and profile morph; allow utility CSS transitions only when they do not compete over the same properties. Preserve reduced-motion semantics and stable set-entry fields. Do not unify two equivalent-looking keyframes solely because their body strings match: independent animation names may be needed to retrigger effects.

### F. Information and message hierarchy are as important as paint

Audit whether each first viewport answers **What am I doing? What changed? What do I press?** Keep regular double-progression rep increments out of program-change/Undo UI; reserve change notices for meaningful structural or load-level decisions. Set logging should not repeat coaching under every set, nor should PR notices fire on mere navigation/restore. These are product semantics, not CSS-only tasks. Issue #418 remains a separate launch blocker until end-to-end prescription provenance is demonstrated.

## 6. Required audit fixtures and metrics

Maintain one permanent visual/component gallery with representative real UI variants, **not mocked labels only**:

- Action: all variants; selected, disabled, pending, destructive, icon-only; keyboard focus.
- Card: normal, inset, hero, interactive, metric, warning; content overflow and selected/pressed states.
- Field: empty, filled, invalid raw draft, units, min/max step, hardware keyboard / mobile IME, 200% text.
- Choice: chip, segmented, tabs, multiselect and summary; accessible name and semantic state.
- Sheet: ordinary, destructive, scrollable, read-only, viewport resize, keyboard, Escape/Back and focus restore.
- Workout: planned, editing, active, completed, skipped, suggested reduction, undo, interruption and resumed set.
- Notification: normal info, pending save, real PR, reversible change, error and persistent toast with dock.

Report for each changed family: before/after source footprint, owner count, computed geometry, text scale, light/dark/theme contrast, clip/overlap evidence, callback parity, UX task completion, screenshot diff and browser gates. Require human review of screenshots, since a green source contract does not prove a cohesive visual result.

## 7. Explicit exclusions / safety

- Do not change progression, exercise selection, history, personal-record calculations, backup formats or stored workout state as part of visual consolidation.
- Do not migrate dynamic theme interpolation without an equivalent verified token mapping.
- Do not force every action into UiAction if it would break native stepper/menu/selection semantics.
- Do not assume an existing 40px/44px declaration means a 40px/44px *effective* hit target. Measure real boxes and overlap at font scaling.
- Do not increase the existing stylesheet/inline/priority debt ceilings to make a new migration pass.
- Do not claim Android, 14/14, responsive screenshot or hosted release sign-off from source inspection.

## 8. Proposed product decisions to approve once, before implementation

1. Adopt the action/choice/card/field/sheet taxonomy in §2 as the single canonical grammar.
2. Keep the user-selected theme and the documented spacing/type/shape scale; create exceptions only with a concrete UX reason.
3. Start with Settings + Gallery + Program settings as a pilot, not Workout.
4. Permit a specialty Workout set-control family to share tokens but keep its own layout/interaction structure.
5. Treat visual snapshots, 200% text, keyboard, actual error states and one completed user journey as required design gates, alongside existing CI.
6. Treat Build 1000 as the audited baseline; keep post-B1000 draft PR #423 unmerged until its controls are reviewed against the new taxonomy.
7. Evaluate progress by **consistency, usable geometry, reduced duplicated ownership and completed behavior**, not number of pass labels.
